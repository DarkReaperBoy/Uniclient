- [ ] [CRITICAL] `votePoll` loops calling the engine once per option index, sending N individual `messages.sendVote` requests for a multi-choice poll. The Telegram API schema (`messages.sendVote peer msg_id options:Vector<bytes>`) requires ALL chosen options in a single call; every call after the first will be rejected server-side, silently dropping all but the first selected answer — `chat_state.dart:1630` ← `AyuGram/api/api_polls.cpp:147` (`Polls::sendVotes` builds a single `MTP_vector<MTPbytes>` with all options)

- [ ] [CRITICAL] `_ensureEnoughTaggedMessages` (line 363) calls `_loadMessages()` synchronously up to 5 times inside a `while` loop without `await` between iterations. `_loadMessages()` modifies `_messages` and `_hasMoreMessages` directly and calls `notifyListeners()`, so the guard condition `_hasMoreMessages` may be stale when evaluated on the next iteration; this can fire 5 rapid consecutive engine reads and trigger 5 widget tree rebuilds before the first one settles — `chat_state.dart:363` ← `AyuGram/history/view/media/history_view_poll.cpp:2708` (reaction-tag filtering loads once, shows a loading state; no loop)

- [ ] [MAJOR] Forum topics "has more" threshold `topics.length >= 100` does not match AyuGram reference. AyuGram initial load requests `kTopicsFirstLoad = 20` items and subsequent pages request `kTopicsPerPage = 500`. Using 100 as the threshold means if the engine returns 20–99 topics (a full initial page), `_forumHasMore` is incorrectly set to `false`, hiding the "load more" path — `chat_state.dart:982,1022,1058,1078` ← `AyuGram/data/data_forum.cpp:40,42` (`kTopicsFirstLoad = 20`, `kTopicsPerPage = 500`)

- [ ] [MAJOR] Every `loadChats()` invocation makes an extra synchronous engine call `_engine.getChatList(archived: true, limit: 1)` solely to probe for archive presence. Since `loadChats()` is triggered by every `onChatSnapshot`, `onAccountList`, and `onConnState` event (debounced but frequent), this doubles the number of engine reads. AyuGram exposes the archive folder as a fixed entry in the dialogs list — no extra probe call — `chat_state.dart:873` ← `AyuGram/data/data_folder.cpp` (archive presence derived from `Folder::shouldBeInChatList()`, no extra request)

- [ ] [MAJOR] 3-second polling timer `Timer.periodic(const Duration(seconds: 3), _refreshMessages)` is started whenever a chat is opened and runs indefinitely. `_refreshMessages` reads all messages from the engine and rebuilds the list on every tick, triggering `notifyListeners()` and a full widget rebuild 20 times per minute. AyuGram Desktop is entirely event-driven with no polling fallback — `chat_state.dart:2135` ← `AyuGram/data/data_changes.cpp` (changes propagated via `Changes::messageUpdated`/`historyUpdated` signals only)

- [ ] [MAJOR] `_senderAvatars` map has no eviction policy. Every group/channel chat open triggers `_loadMemberAvatars` which paginates up to 1000 members and stores their base64 thumbnails. The map is only cleared when switching to a DM (`_senderAvatars.clear()` at line 967). Opening multiple group chats in a session accumulates unbounded memory proportional to total members seen — `chat_state.dart:35,967,1941` ← `AyuGram/data/data_peer.cpp` (user photos held via `CloudImage` with ref-counted sessions, automatically evicted)

- [ ] [MAJOR] No event subscriptions for live forum topic mutations. The constructor only subscribes to `onMsgReceived/Edited/Deleted/Status`, `onChatUpdated/Removed`, etc. Forum topic created/edited/deleted/closed changes are never received in real-time; the topic list only refreshes on explicit `refreshForumTopics()` or `openForum()`. AyuGram propagates these via `Data::Changes::topicUpdated` and `topicRemoved` — `chat_state.dart:133` ← `AyuGram/data/data_changes.cpp:topicUpdated`, `AyuGram/data/data_forum.cpp:applyTopicDeleted`
